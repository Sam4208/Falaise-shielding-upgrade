37  /// \brief SuperNEMO tracker clustering data model
38  //
39  // The tracker hits are initialy sorted, by the so-called tracker
40  // pre-clustering algorithm, within time bunches of typical
41  // duration ~10 us (see the configuration of the
42  // snemo::processing::base_tracker_clusterizer of snemo::processing::base_tracking_driver classes).
43  //
44  // The first expected bunch is the so-called *prompt* pre-cluster
45  // which contains all the tracker prompt hits that are collected
46  // by the prompt trigger within a ~10 us time coincidence
47  // window. Then comes eventually *delayed* pre-clusters that are
48  // also collected by bunches of ~10 us with some arbitrary delay after
49  // the prompt bunch. An event should contains one and only one
50  // prompt pre-cluster and event can have zero or several *delayed*
51  // pre-clusters.
52  //
53  // ~10 us ~10 us ~10 us
54  // <-----> <----> <------>
55  // --[o-oo-oo]-----------[o-o--o]-------[o---oo-o]------------> time
56  // "prompt" "delayed" "delayed"
57  // (id==0) (id==1)
58  //
59  // The prompt pre-cluster generally gathers all prompt hits from
60  // both sides of the source frame. This is because we expect
61  // several prompt charged particle tracks traversing any location
62  // within the tracking chamber, and triggering tracker drift cells
63  // everywhere in the detector, regardless of the side with respect
64  // to the source frame. It is expected that the full event
65  // topology should be reconstructed taking into account tracks
66  // from both sides. This is obviously the case when we search for
67  // double-beta decay candidate events.
68  //
69  // side==0 side==1
70  // +---------+---------+
71  // | o ! |
72  // | ! |
73  // | ! |
74  // | !o |
75  // | ! oo |
76  // | ooo! ooooo |
77  // | ooo ! oooo|
78  // |ooo ! o|
79  // | ! |
80  // | ! |
81  // | ! |
82  // | ! |
83  // | ! o |
84  // | ! |
85  // | ! o |
86  // | ! |
87  // | ! |
88  // | ! |
89  // +---------+---------+
90  //
91  // Delayed clusters are built independantly on their own side of
92  // the source frame. The purpose of these clusters is the search
93  // for delayed tracks mainly from the Bi214-Po214 decays which are
94  // one of the more critical background in the experiment. Each
95  // delay cluster has its own delayed cluster ID.
96  //
97  // The tracker clustering algorithm aims to gathered some tracker
98  // hits within a given pre-cluster and build from them a
99  // collection of tracker clusters. However, several clustering
100  // solutions may exist so the final product of the clustering
101  // algorithm consists in a collection of clustering solutions
102  // (a.k.a. clustering scenarii). The tracker clustering data model thus
103  // stores a collection of solutions. A subset of these solutions
104  // corresponds to the clusterization of the prompt pre-cluster:
105  // they are tagged with a dedicated *prompt* flag. Other subsets of
106  // clustering solutions may have been built for the various
107  // delayed pre-clusters. In such case, each solution is tagged
108  // with a dedicated *delayed* flag and an unique *delayed cluster
109  // ID*.
110  //
111  // The contents of a typical tracker clustering data object may
112  // looks the following, where the prompt pre-clustered has been
113  // processed by the clustering algorithm which produced three
114  // different clustering scenarii, namely solution 0, 1 and
115  // 2. Then, the two delayed pre-clusters have also been processed,
116  // the first one being associated with two possible solutions (3
117  // and 4) and the second one with only one solution (5):
118  //
119  // [solution #0] prompt
120  // [solution #1] prompt
121  // [solution #2] prompt
122  // [solution #3] delayed cluster Id = 0
123  // [solution #4] delayed cluster Id = 0
124  // [solution #5] delayed cluster Id = 1
125  //
126  //
